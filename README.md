# webrtc-multidet-demo

Real-time WebRTC multi-object detection demo (Phone → Browser → Inference → Overlay)

One-line goal: real-time multi-object detection on live video streamed from a phone via WebRTC, overlayed in the laptop browser. Two modes:
- **WASM mode (default):** on-device inference in the laptop browser using `onnxruntime-web` (quantized model, 320×320, ~10–15 FPS).
- **Server mode:** laptop browser samples frames and sends to Python server (CPU ONNX Runtime). Server returns per-frame results via WebSocket.

## Docker & Compose
```bash
docker compose up --build
```
This exposes the Vite app at http://localhost:3000 and the AIORTC backend at http://localhost:8000. For remote phone access over HTTPS, run a tunnel such as `ngrok http 3000` and use the forwarded URL.

## One-command start
```bash
git clone <this-repo>
cd webrtc-vlm-demo
./start.sh               # defaults to MODE=wasm
# or
MODE=server ./start.sh
```
Then open **http://localhost:3000** on your laptop. A QR code appears — scan it with your phone to join as the camera publisher. Grant camera permission; you should see live overlays on the laptop.

### If phone can’t reach laptop
- Ensure both are on the same Wi‑Fi; OR
- Run a tunnel: `./start.sh --ngrok`. Use the ngrok URL on your phone.

## Deliverables in this repo
- `docker-compose.yml`, `start.sh` (convenience, one-command start)
- **WASM mode** (no GPU required) and **server mode** (Python CPU) — switch with `MODE=wasm|server`
- `bench/metrics.json` generated by a 30s bench: `./bench/run_bench.sh --duration 30 --mode wasm|server`
- Backend metrics are aggregated per device. Each browser/device combination is assigned a unique ID based on its user agent, and the final `metrics.json` groups statistics under these IDs.
- **README appendix** (below) with design choices, low-resource path, and backpressure
- A simple signaling server (WebSocket) is embedded in the `web` service

## Phone join
1. Open `http://localhost:3000` on the laptop.
2. Scan the QR code from your phone (Chrome on Android / Safari on iOS).
3. Tap “Join as Camera”. Grant camera permission. The phone publishes a WebRTC video track to the laptop viewer.
4. Laptop page runs inference (WASM) or forwards frames to the Python server. Overlays draw in near real-time.

## Metrics & Bench
- **Per-frame JSON (server → client)** over WS in server mode:
  ```json
  {
    "frame_id": "string_or_int",
    "capture_ts": 1690000000000,
    "recv_ts": 1690000000100,
    "inference_ts": 1690000000120,
    "detections": [
      {
        "id": 1,
        "label": "person",
        "score": 0.93,
        "xmin": 0.12,
        "ymin": 0.08,
        "xmax": 0.34,
        "ymax": 0.67
      }
    ]
  }
  ```
  The backend also persists these entries per device. The most recent entry
  for a device can be fetched via HTTP:

  ```bash
  curl "http://localhost:8000/?device_id=<id>"
  ```
  which returns a JSON object in the same format as above.
- **E2E latency per frame:** `overlay_display_ts - capture_ts`
- **Server latency:** `inference_ts - recv_ts`
- **Network latency:** `recv_ts - capture_ts`
- **Processed FPS:** frames with detections displayed / seconds
- **Bandwidth:** the laptop web server samples WebRTC stats and data channel bytes; also see Chrome DevTools → `webrtc-internals`

Run:
```bash
./bench/run_bench.sh --duration 30 --mode wasm
# or
./bench/run_bench.sh --duration 30 --mode server
cat bench/metrics.json  # includes median/p95 for e2e, server and network latency
```

## Appendix: Design choices, low-resource mode, backpressure

**Design.** A minimal WebRTC topology:
- Phone → (WebRTC peer) → Laptop browser (viewer). Signaling via WebSocket in the `web` container.
- **WASM mode:** Viewer runs `onnxruntime-web` (wasm backend). Model: quantized tiny YOLO (320×320). Postprocessing in JS (NMS).
- **Server mode:** Viewer samples the latest frame at a fixed rate (default 12 FPS), encodes to JPEG, and sends via WebSocket to Python. Python (ONNX Runtime CPU) runs detection and returns JSON results per frame. Viewer overlays boxes and records timestamps.

**Low-resource path.**
- Downscale to 320×240 display; inference at 320×320 model input.
- Target 10–15 FPS processing; frame-thinning by always keeping only the most recent sampled frame.
- Use `tf32`/quantized weights (we supply tiny model by default).
- WASM backend (no GPU needed).

**Backpressure policy.**
- Fixed-length queue (length=1). When a new frame is available while inference is busy, drop the old frame and process the newest.
- In server mode, client won’t send a new frame until it has either received results or a timeout expired, preventing server overload.
- Adaptive sampling: dynamically reduce sample FPS when median latency rises above a threshold.

**Fairness / CPU on modest laptop.**
- With 320×240 preview and 320 input, i5-class CPU typically sustains 10–14 FPS in WASM; server mode similar or slightly faster (C++ kernels).
- Document CPU usage with `top/htop`; include your notes in README once you run locally.

**Troubleshooting.**
- If overlays misalign: make sure `capture_ts` (ms) is consistent, and the frame’s `frame_id` is used to match detections to the displayed frame.
- If connect fails: ensure same Wi‑Fi or run ngrok; check browser console logs; try Chrome on both devices.
- If CPU high: lower sample FPS (`SAMPLE_FPS` env) or set `VIDEO_WIDTH=320` `VIDEO_HEIGHT=240` when starting the app.
